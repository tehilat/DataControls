# רדאר - בקרות איכות נתונים

מערכת גנרית להגדרה ולהרצה של בקרות איכות נתונים, במונחים עסקיים, בלי SQL

**מגישה:** תהילה טננולד

**תאריך:** 14/11/2026

## 1. סקירה ותחום הנתונים

**רדאר** מאפשרת למשתמש עסקי להגדיר בקרות איכות נתונים בלי לכתוב SQL ובלי להכיר את שמות הטבלאות. המשתמש בוחר ישות,
שדות ותנאים בעברית, מריץ את הבקרה מול SQL Server, ומקבל את הרשומות החריגות עם סיבה קריאה לכל רשומה.
בשלב ב' אפשר לתאר בקרה במילים, ולקבל הצעה שמוצגת לאישור לפני שמירה.

**תחום הנתונים: צי רחפני משלוחים.** חמש ישויות עסקיות בסכמה `ops`:

| ישות | רשומות בדוגמה | תפקיד |
|---|---|---|
| מוקד | 5 | מוקד הפעלה שממנו יוצאים הרחפנים (פעיל / סגור) |
| רחפן | 10 | כושר נשיאה, טווח טיסה, סטטוס, מועדי תחזוקה. שייך למוקד |
| מפעיל | 6 | מפעיל מורשה: מספר רישיון, תוקף, פעיל |
| לקוח | 8 | פרטי קשר וכתובת מסירה |
| משלוח | 22 | משקל, מרחק, זמני יציאה ומסירה, סטטוס. מקושר לרחפן, למפעיל וללקוח |

**הקשרים** (כולם רבים-ליחיד, מהילד להורה): משלוח → רחפן → מוקד, משלוח → מפעיל, משלוח → לקוח.
בזכות זה, בקרה על משלוח יכולה להשתמש בשדות כמו "כושר נשיאה (רחפן)" או "מוקד פעיל (רחפן › מוקד)".

הנתונים כוללים רשומות שגויות מבודדות (כל אחת נתפסת רק בבקרה שלה) ומקרי גבול תקינים. התאריכים יחסיים ליום הטעינה,
כך שהבקרות נשארות נכונות בכל יום. סקריפט אופציונלי (`06`) מוסיף ישות שישית, "התראת מזג אוויר", דרך Metadata בלבד.

## 2. ארכיטקטורה ומנגנון הבקרות

### שכבות

```
Angular 22             ממשק בעברית: רשימת בקרות · עורך תנאים רקורסיבי · תוצאות · צור בעזרת AI
   │ /api (proxy)
.NET 10 Web API
  Api                  Controllers · DTOs · OpenAPI · שגיאות ProblemDetails בעברית
  Application          DefinitionBinder · שירותי בקרות, הרצות, קטלוג והצעות AI · ממשקים
  Infrastructure       SqlMetadataProvider · SqlQueryBuilder · SqlControlRunner · AI HTTP client
  Domain               ControlDefinition (group / rule / operand) · MetadataCatalog
   │ Dapper                                │ HTTP
SQL Server: ops · meta · ctl               Python ai-service: PromptBuilder · AiProvider (Mock)
```

שלוש סכמות: `ops` לנתונים העסקיים, `meta` לקטלוג העסקי, `ctl` לבקרות, להרצות ולתוצאות. כל שכבה במנוע נמצאת מאחורי
ממשק (`IMetadataProvider`, `IQueryBuilder`, `IControlRunner`, `IAiControlGenerator`).

### Metadata: המפתח לגנריות

הטבלאות `meta.Entities`, `meta.Fields`, `meta.FieldOptions`, `meta.Relations`, `meta.Operators` ו-`meta.DataTypeOperators`
ממפות מונחים עסקיים בעברית ("משלוח", "משקל חבילה", "הוא", "לפני") לטבלאות, לעמודות, לקשרים ולאופרטורים המותרים לכל סוג
שדה. ב-`meta` לא נשמר SQL. אין בקוד (C#, Python או Angular) אף שם של טבלה או עמודה עסקית. ישות חדשה מתווספת בשורות
ב-`meta` בלבד, והיא מופיעה מיד בממשק, במנוע ובקטלוג שנשלח ל-AI.

### בקרה = נתונים, לא SQL

בקרה נשמרת ב-`ctl.Controls` כעץ תנאים ב-JSON:

```json
{ "version": 1, "rootEntity": "Delivery", "condition":
  { "type": "rule", "field": "PackageWeightKg", "operator": "gt",
    "compareTo": { "kind": "field", "field": "Drone.MaxPayloadKg" } } }
```

צומת הוא `group` (AND / OR, מקונן) או `rule` (שדה, אופרטור, ערך השוואה). ערך ההשוואה יכול להיות ערך קבוע, שדה אחר,
"היום ± ימים" או "עכשיו". נתיב שדה עובר דרך קשרים (`Drone.Hub.IsActive`).

### הצינור

```
meta.*  +  ctl.Controls.DefinitionJson
   │
   ▼  ControlDefinitionSerializer   הופך את ה-JSON למודל
   ▼  DefinitionBinder              ולידציה מול הקטלוג: שדות, אופרטור מול סוג, טווחי ערכים
   ▼  SqlQueryBuilder               שאילתת SELECT עם פרמטרים, וחיבור קשרים לפי meta.Relations
   ▼  SqlControlRunner              הרצה תחת EXECUTE AS USER ואז REVERT, עם timeout ו-TOP
   ▼  ViolationReasonBuilder        סיבה בעברית לכל רשומה חריגה
   ▼  ctl.ControlRunViolations      שמירת החריגות: paging, חיפוש, סינון ומיון לפי סוג
```

דוגמה לסיבה: "משקל חבילה (4.5 ק"ג) גדול מ-כושר נשיאה (רחפן) (3 ק"ג)". כל שגיאות הוולידציה מוחזרות יחד, בעברית,
עם נתיב JSON (למשל `condition.children[1].field`), והממשק מציג אותן על התנאי עצמו.

ה-Binder משמש גם לשמירה, גם להרצה, גם לתצוגה מקדימה וגם להצעות AI, כך שיש מקום אחד לכל כללי התקינות.
מספר החריגות האמיתי מוחזר תמיד (`COUNT(*) OVER ()`), גם כשהתוצאה נחתכת במגבלת השורות.

### אבטחה

- **Whitelist:** כל מזהה (טבלה, עמודה, קשר) מגיע רק מה-Metadata, שנבדק גם מול `sys.columns` ומול regex של מזהה.
  ישות או שדה שלא עומדים בזה נפסלים מהקטלוג. אין API שמקבל SQL או שם פיזי.
- **פרמטרים:** כל ערך הוא פרמטר. טקסט נשלח תמיד כ-nvarchar, כולל escape ל-`LIKE`. אין שרשור ערכים ל-SQL.
- **הרשאות מינימליות:** כל הרצה מתבצעת תחת `EXECUTE AS USER = 'controls_runner'`, שיש לו רק SELECT על `ops`.
  `99_verify.sql` מוכיח ש-UPDATE על `ops` ו-SELECT על `ctl` נחסמים.
- **SELECT בלבד**, עם timeout ומגבלת שורות. אם לא ניתן לאמת שההתחזות בוטלה, ה-connection pool מתרוקן.
- **אופרטור מול סוג:** אין "גדול מ" על טקסט, אין "מכיל" על מספר. ניסיונות injection בנתיבים, בערכים, באופרטורים
  וב-Metadata זדוני מכוסים בבדיקות.
- ה-SQL שנוצר לא נחשף ב-API, כי הוא מכיל שמות פיזיים.

## 4. שלב ב': הגדרת בקרה בשפה חופשית

### הזרימה

```
Frontend               המשתמש כותב במסך "צור בעזרת AI": "רחפן פעיל במוקד סגור"
   ▼  POST /api/ai/suggest-control {text}
.NET AiSuggestionService     בונה קטלוג עסקי, בלי שמות פיזיים, וקורא ל-IAiControlGenerator
   ▼  POST /generate-control {text, catalog}
Python ai-service      PromptBuilder · AiProvider (Mock) · ולידציה מול הקטלוג
   ▼  {definition, explanation, confidence, warnings}
.NET                   ולידציה עם אותו Binder של שלב א', ותקציר בעברית מהקטלוג
   ▼  AiSuggestionDto
Frontend               המשתמש בודק ← "פתח בעורך" ← תצוגה מקדימה ← שמירה (Source = AI) ← הרצה
```

### מבנה התשובה

```json
{ "definition": { "version": 1, "rootEntity": "Drone", "condition": { ... } },
  "isValid": true, "rootEntity": "Drone", "rootEntityDisplayName": "רחפן",
  "summary": "יאותרו רחפנים שבהם סטטוס רחפן: בשירות וגם מוקד פעיל (מוקד): לא.",
  "explanation": "הבקרה תאתר רחפנים בסטטוס 'בשירות' שמשויכים למוקד שאינו פעיל.",
  "confidence": 0.9,
  "warnings": ["'רחפן פעיל' פורש כרחפן בסטטוס 'בשירות'."],
  "validationErrors": [] }
```

`definition` הוא בדיוק אותו DefinitionJson של שלב א'. `summary` נבנה ב-.NET מהקטלוג, ולא ע"י ה-AI, ולכן הוא מתאר את מה
שבאמת ירוץ. בקשה לא מזוהה מחזירה `definition: null` עם הסבר. שירות AI לא זמין מחזיר 503 בעברית, וכל השאר ממשיך לעבוד.
ה-Mock מזהה 5 בקשות לדוגמה, למשל "משקל מעל כושר נשיאה", "לקוח בלי טלפון ובלי אימייל" ו"מפעיל עם רישיון שפג".

### הפרדה מהמנוע

- תשובת ה-AI היא **קלט לא מהימן**: היא עוברת ולידציה ב-Python ואז ב-`DefinitionBinder` של ה-.NET. SQL לא נוצר ממנה ישירות.
- ה-AI **רק מציע**: שירות ההצעות לא תלוי ב-repository או ב-runner, ולכן אינו יכול לשמור או להריץ.
- מנוע הבקרות לא יודע מאיפה הגיעה הגדרה, ושירות ה-AI לא ניגש ל-DB. החיבור הוא ממשק אחד, `IAiControlGenerator`.
- "מה נשלח ל-AI" מוצג במסך (`/api/ai/prompt-preview`): קטלוג עסקי, כללים ומבנה התשובה, בלי שמות טבלאות.

### החלפת מודל

מוסיפים מחלקה שמממשת `AiProvider` ב-`ai-service/providers/` (מתודה אחת: `generate`), רושמים אותה ב-`_PROVIDERS`,
ובוחרים אותה במשתנה הסביבה `AI_PROVIDER`. ה-prompt, מבנה התשובה, הוולידציה וה-.NET לא משתנים.

## 5. הנחות, מגבלות והרחבות

**הנחות עיקריות:** המשתמש לא מכיר את מבנה ה-DB; ה-Metadata מתוחזק ע"י גורם טכני; רשומה חריגה = התנאי מתקיים;
השוואה ל-NULL לא מתקיימת (משתמשים ב"ריק"); "היום" ו"עכשיו" לפי שעון שרת ה-SQL.

**מגבלות:**
- **קשרים רבים-ליחיד בלבד.** אין "קיים / לא קיים" על קשר הפוך, ולכן אי אפשר כרגע להגדיר "משלוח שיצא בזמן התראת מזג
  אוויר פעילה במוקד שלו" (משלוח → רחפן → מוקד ← התראות).
- אין צבירות (COUNT / SUM), אין חישובים בתנאים ("שדה × 1.1"), ואין אופרטורים "בין" ו"אחד מתוך".
- אין אימות משתמשים, תזמון הרצות או מדיניות שמירה להרצות. Metadata מנוהל בסקריפט, לא במסך.
- ה-Mock מזהה רק תרחישים מוגדרים מראש, ואין שיחה מתמשכת עם ה-AI.

**הרחבות מתוכננות:**
- **תנאי `exists` על קשר הפוך** (`version: 2`): צומת עם תנאים פנימיים ו-operand מסוג `outer` לשדות הרשומה החיצונית,
  שמתורגם ל-`EXISTS` עם תת-שאילתה מתואמת. בלי שכפול רשומות, ועם אותו whitelist. בסיס גם לצבירות.
  חלופה מיידית: View שמחזיר שורה אחת לכל רשומת בסיס ונרשם ב-Metadata.
- מסך ניהול Metadata וסריקת `INFORMATION_SCHEMA` כטיוטה; אימות משתמשים ותפקידים; תזמון והתראות; ייצוא תוצאות.
- מודל AI אמיתי, שיחה ועריכה בשפה חופשית, וסינון הקטלוג לפי רלוונטיות בקטלוגים גדולים.

**אופן העבודה:** מפרט מפורט לפני קוד (`docs/db-instructions.md`); תוכנית לכל שלב; שלבים קטנים, שכבה אחת בכל פעם,

**דוגמאות לכיוון ותיקון של הכלי:** התאמה ל-SQL Express עם אימות Windows (`WITHOUT LOGIN` ו-`EXECUTE AS` במקום משתמשים
עם סיסמה); שינוי `ops.Operators` ל-`ops.Pilots` כדי למנוע בלבול עם אופרטורי ההשוואה; תאריכים יחסיים כדי שהבקרות לא
"יתיישנו"; מיון וסינון לפי סוג נתון (ולא כמחרוזת); ממצאי בדיקת UI ידנית (גלישה, מזהה רשומה, ניסוח הסיבות, החלפת וגם/או);
ותיעוד מגבלת הקשרים שהתגלתה בבדיקה ידנית.

**מה נבדק ידנית:** כל תוכנית וכל סיכום שלב; ה-UI בדפדפן (RTL, רשימה וסינון, מספרי החריגות מול `99_verify.sql`, בקרה חדשה
מאפס עם תצוגה מקדימה, שמירה והרצה); מסך התוצאות וההיסטוריה; וזרימת ה-AI, כולל מצב שבו השירות אינו זמין.
